# SC14448 peripheral cross-references

Status: **offline static analysis.**  Generated by
`tools/cr16_peripheral_xrefs.py`; the machine-readable form is
`tools/reports/peripheral-xrefs.json` and
`tools/tests/test_cr16_peripheral_xrefs.py` checks that rerunning the tool
reproduces it.

This file lists **what the tools can prove about each access**, and where the
search stops.  It is not a hardware map: the meaning of every register below
is still unknown (L2 evidence only).

---

## 1. What the scanner resolves and what it does not

| Access shape | Resolved? | Evidence |
|---|---|---|
| `storw`/`loadw`/`storb`/`loadb`/`stord`/`loadd` with an `abs20` operand | **yes**, address from the instruction bytes | L2 |
| address built by `movd $imm:l,(rp)` | **yes** for the literal; linked to a following `disp(rp)` only while that pair is not reloaded | L2 |
| `disp(rp)` where the pair came from somewhere else | **no** — recorded as `RUNTIME_ADDRESS` with the expression | — |
| address computed arithmetically from several registers | **no** | — |

## 2. `0x000F6002` — the polled address

| Site | Instruction | Access |
|---|---|---|
| `0x25FAE` (normal) / `0x26764` (p2test) | `loadw 0xf6002:m,r0` | 16-bit **read** |

**There is no other access to `0x000F6002` in either image** — no write, no
second reader.  The scan covers all `abs20` accesses and all `movd` bases, so
this absence is meaningful for those two shapes (and only for them).

That is consistent with a status bit maintained by hardware, but it does not
prove it: a value written through a computed pointer would not appear here.

## 3. `0x000F6400`, `0x000F6402`, `0x000F5402`

| Address | Site | Instruction | Value |
|---|---|---|---|
| `0x000F6400` | `0x255E` | `storw $0x0:s,0xf6400:m` | `0x0000` |
| `0x000F6402` | `0x2566` | `storw r0,0xf6402:m` (`r0 = 0x00F0`) | `0x00F0` |
| `0x000F5402` | `0x1934` | `storw r0,0xf5402:m` | `0x2000` |
| | `0x25B0` | | `0x0400` |
| | `0x3A28` | | `0xFFFF` |
| | `0x26034` | | `0x0400` |
| | `0x289A8` | | `0x0100` |
| | `0x28B00` | | `0x2000` |
| | `0x28CE8` | | `0x0400` |

`0x000F6400` and `0x000F6402` each have exactly one writer and no reader.
`0x000F5402` is written from seven places with four different values, which
makes it the most likely *control* register of the group; its function is
still unknown.

The site at `0x28CE8` sits directly after a read of `0x000F6006`
(`0x28CDE`) and writes `0x0400`, the same value as `0x25B0` and `0x26034`.

## 4. `0x000F6006` — the pulsed register

| Site | Instruction | Value |
|---|---|---|
| `0x1348` | `storw r2,0xf6006:m` with `r2 = 0x0080` (`0x1344`) | `0x0080` |
| `0x145C` | `storw r0,0xf6006:m` with `r0 = 0x0080` (`0x1458`) | `0x0080` |
| `0x2602C` | `loadw 0xf6006:m,r0` | read, result discarded |
| `0x28CDE` | `loadw 0xf6006:m,r0` | read, then `0x0400` written to `0x000F5402` |

Two independent writers exist (`0x1348` inside the routine `0x1330`,
`0x145C` inside the neighbouring routine), both writing **`0x0080`**.  In
`0x2558` the same value is written through a `movd`-loaded base
(`0x258C`), and `0x25B4` writes `0` to it — the only clear.

The `0x1330` routine reads `[0x00D6]` (a 32-bit cell) and tests it against
`0x01027F80` (`0x133A`); only on a match, and only when `r2 == 0`
(`0x1342`), does it write `0x80`.  So the `0x80` write is behind a guard on
a data cell, not unconditional.

## 5. `0x00FF6006` and `0x00FF5406` — through register pairs

Both are reached only through `movd` bases, so the scan links them:

| Address | Base set at | Instruction |
|---|---|---|
| `0x00FF6006` | `0x2582` | `movd $0xff6006:l,(r1,r0)` |
| | `0x258C` | `storw r2,0x0:s(r1,r0)` — `0x0080` |
| | `0x25AA` | `loadw 0x0:s(r1,r0),r2` — discarded |
| | `0x25B4` | `storw $0x0:s,0x0:s(r1,r0)` — `0` |
| `0x00FF5406` | `0x2596` | `movd $0xff5406:l,(r4,r3)` |
| | `0x259C` | `loadw 0x0:s(r4,r3),r5` |
| | `0x25A2` | `storw r5,0x0:s(r4,r3)` after `andw $0xf0ff` |

Other `movd` bases into the same blocks: `0xFF5404` (`0x1918`), `0xFF400A`
(`0x2500`, the `0x24F8` bit loop), `0xFF4000` (`0x28A5C`, `0x28A78`),
`0xFF4010`, `0xFF401C`, `0xFF4004`, `0xFF4810`…`0xFF4868` (eleven GPIO-like
addresses), `0xFF5800`…`0xFF580C`, `0xFF7052`…`0xFF7080`, `0xFF4960`.

The `0x000Fxxxx` (abs20) and the `0x00FFxxxx` (movd) blocks are **different
addresses**; nothing in the code proves they alias the same hardware.

## 6. `0x00FF400A` — inside `0x24F8`

Written only inside the routine itself (`0x251A`, `0x2534`); the base is
loaded at `0x2500`.  Two other routines take bases in the same block
(`0xFF4000`, `0xFF4010`, `0xFF401C`), so `0xFF40xx` is a block of related
registers, not a single one.

## 7. `0x01000000` — no reader found

The base appears at `0x25C4` (`0x25BA`), `0x2604`, `0x2E72`, `0x2F98`,
`0x36BA`, `0x36EC`.  The scanner finds those `movd` literals but **no
memory access** based on them is linked: `0x25CE` does `addd (r7,r6),(r5,r4)`
before the `storw r2,0x0:s(r5,r4)` at `0x25D0`, so the final address exists
only at run time.  The same holds at the other five literals.  No `abs20`
operand anywhere in either image points at or above `0x01000000`; that is
consistent with this area being reachable only through a register pair, but
it is not proof of what the area is.

Therefore: writers through `0x25BA` are known (see
`fon-dialog-peripheral-init.md`), **readers are not found and cannot be
excluded**.

## 8. Access widths

Every record carries the width of the *operation*:

* `0x000F6002`, `0x000F6400`, `0x000F6402`, `0x000F5402`, `0x000F6006` are
  accessed with `storw`/`loadw`, i.e. **16-bit**;
* `0xFF6006`, `0xFF5406`, `0xFF400A` are also `storw`/`loadw` (16-bit),
  reached through 32-bit addresses in a register pair (`movd …:l`).

No 32-bit peripheral access to these registers exists in either image.
