# SC14448 peripheral cross-references

Status: **offline static analysis.**  Generated by
`tools/cr16_peripheral_xrefs.py` (version `cr16-peripheral-xrefs/3`); the
machine-readable form is `tools/reports/peripheral-xrefs.json` and
`tools/tests/test_cr16_peripheral_xrefs.py` checks that rerunning the tool
reproduces it byte for byte.

This file lists **what the tools can prove about each access**, and where the
search stops.  It is not a hardware map: the meaning of every register below
is still unknown (L2 evidence only).

Nothing here was observed on hardware.  All statements are L1/L2 (bytes and
static decoding).

---

## 1. How the scanner classifies an access

Every memory instruction gets exactly one `address_kind`:

| `address_kind` | Meaning | Can it be a peripheral address? |
|---|---|---|
| `RESOLVED` | the address is a constant proven by the machine code: an `abs20`/`abs24` immediate field, or a register pair holding a proven constant within the same basic block | yes |
| `SYMBOLIC` | an expression over a proven base, e.g. `0x01000000 + 2*r3`; **never** evaluated into a single number | possibly, not determinable statically |
| `UNKNOWN` | the base registers are not known statically | not determinable |
| `STACK` | `disp(sp)` — the stack frame | no |
| `INDEXED` | `[r12]`/`[r13]` indexed forms | not determinable |
| `PC_RELATIVE` | `disp(ra)` — relative to the return address | no (code/literal pool) |
| `ADDRESS_LOAD` | `movd $imm,(rp)` — a literal, **not** a memory access | n/a |

Model of the register state (deliberately conservative):

* linear disassembly is cut into basic blocks; **every block starts with an
  all-UNKNOWN state**, so no value crosses a block boundary, a call, a return,
  an indirect jump or a gap between Intel-HEX runs.  This version never
  inherits a state across an edge, which can only lose a link, never invent
  one;
* `movd $imm:l,(rp)` makes the pair a known constant; `movd $imm:m,(rp)`
  makes only the high half known, so the pair is *not* a constant;
* writing either half of a pair, or loading into one of its registers,
  invalidates the pair;
* a base plus an index (`movzw` / `ashud` / `addd`) becomes `SYMBOLIC`, with
  the factor accumulated (`ashud $1` twice is `4*r1`, not `2*2*r1`);
* the tool never converts `UNKNOWN` or `SYMBOLIC` into a numeric address.

Operand forms recognised (from `cr16-opc.c` `LD_STOR_INS` and the `abs24`
relocation in `bfd/elf32-cr16.c`):

| Form | Bytes | Address source | Checked against |
|---|---|---|---|
| `<abs>:m` | 4 | `(b0 & 0xF) << 20 \| word1` | all 38 occurrences |
| `<abs>:l` | 6 | `abs24_address()` (`opc20`) | all 161 / 170 occurrences, and the assembler output for `0x0fffff`, `0x100000`, `0xff4c00` |
| `<disp>:s\|m(rN,rM)` | 2–3 | register pair + displacement | synthetic fixtures |
| `<disp>:s\|m(rN)` | 1–3 | single register + displacement | `[r12]`/`[r13]`/`(ra)` forms |
| `(sp)` | 1–3 | stack frame | — |

`READ + WRITE + RMW` equals the classified total, and the address kinds sum
to the same number; `ADDRESS_LOAD` is deliberately outside both.

**Unsupported memory instructions** are listed individually in the report
under `memory_unsupported`, with address, bytes, mnemonic, operands and the
reason: `loadm` (13 / 1) and `loadmp` (3 / 0).  `storm`/`stormp` are known
forms but do not occur in either image.

**Completeness statement.** Every decoded instruction within the supported
memory forms is classified, and the forms this scanner does not decode are
listed explicitly rather than dropped.  `unclassified` is empty because it
only ever holds instructions inside `ACCESS` whose operand failed to parse.

That is **not** the same as "every access is known":

* 2 812 operations in `normal` are `UNKNOWN` and 8 are `SYMBOLIC`;
* 16 instructions use `loadm`/`loadmp`, whose operand form is not decoded;
* the implicit stack traffic of `push`/`pop` is not counted.

**Version history.**

| Version | Change | normal RESOLVED | normal operations |
|---|---|---|---|
| 2 | `disp:s(rp)` operands, per-block pairs | 1 346 | 4 301 |
| 2.1 | correct `addd` destination; every register-writing instruction invalidated; address operand chosen by direction | 1 280 | 4 301 |
| 2.2 | widening forms write the **second** operand (was the first); `sbit`/`cbit` counted as RMW; `tbit` counted as a bit read; unsupported memory forms listed | 951 | 5 167 |

The two totals are not directly comparable, because version 2.2 counts
operations that version 2.1 did not count at all.  Measured against the
previous report, instruction by instruction:

| Quantity | 2.1 | 2.2 | Comment |
|---|---|---|---|
| `RESOLVED` READ+WRITE rows | 712 | **885** | +173, all of them `tbitw`/`tbitb` that were previously not an access |
| `RESOLVED` rows that changed or disappeared | — | **0** | no address was lost or altered |
| memory operations counted | 4 301 | 5 167 | +866: 567 `tbit`, 299 `sbit`/`cbit` |

So the arithmetic drop of the `RESOLVED` counter from 1 280 to 951 is the
**denominator** growing, not addresses disappearing.  The `movzw` fix
removed a way to *produce* a false address; it did not invalidate any
address this firmware actually states.  Measured: of the 269 `movzw`/`movxw`
pair-destination forms in `normal` and 206 in `p2test`, **none** uses that
pair as an address base later in the same block (the pair is always a
*literal* operand or a copy destination).  The fix is therefore a correctness
fix for the rule, demonstrated by the synthetic counterexample in
`fon-dialog-cr16-register-effects.md` §2, not a change to the map of this
firmware.

`0x258C`, `0x25AA`, `0x25B4`, `0x259C`, `0x25A2`, `0x25FAE` and `0x1348`
keep their `RESOLVED` addresses; `0x25D0` remains `SYMBOLIC`
(`0x01000000 + 2*r3`).

## 2. `0x000F6002` — the polled address

| Site | Instruction | Access |
|---|---|---|
| `0x25FAE` (normal) / `0x26764` (p2test) | `loadw 0xf6002:m,r0` | 16-bit **read** |

No other read, no write and no `ADDRESS_LOAD` for `0x000F6002` exists in
either image.

That is consistent with a status bit maintained by hardware, but it does not
prove it, and it does not prove that *nothing* writes the address: a value
written through an `UNKNOWN` or `SYMBOLIC` pointer would not be visible.
Correct phrasing: *no writers were found among the resolved forms; indirect
and computed accesses remain unexamined.*

## 4. `0x000F6006` — the abs20 register

| Site | Instruction | Value |
|---|---|---|
| `0x1348` | `storw r2,0xf6006:m` with `r2 = 0x0080` (`0x1344`) | `0x0080` |
| `0x145C` | `storw r0,0xf6006:m` with `r0 = 0x0080` (`0x1458`) | `0x0080` |
| `0x2602C` | `loadw 0xf6006:m,r0` | read, result discarded |
| `0x28CDE` | `loadw 0xf6006:m,r0` | read, then `0x0400` written to `0x000F5402` |

Two independent writers exist (`0x1348` inside the routine `0x1330`,
`0x145C` inside the neighbouring routine), both writing **`0x0080`**
(`p2test`: `0x0DBE`, `0x0ED2`; readers `0x267E2`, `0x27C96`).

The `0x1330` routine reads `[0x00D6]` (a 32-bit cell) and tests it against
`0x01027F80` (`0x133A`); only on a match, and only when `r2 == 0`
(`0x1342`), does it write `0x80`.  So the `0x80` write is behind a guard on
a data cell, not unconditional.

## 5. `0x00FF6006` and `0x00FF5406` — through register pairs

| Address | Base set at | Instruction | Access |
|---|---|---|---|
| `0x00FF6006` | `0x2582` | `movd $0xff6006:l,(r1,r0)` | `ADDRESS_LOAD` |
| | `0x258C` | `storw r2,0x0:s(r1,r0)` — `0x0080` | 16-bit write |
| | `0x25AA` | `loadw 0x0:s(r1,r0),r2` — discarded | 16-bit read |
| | `0x25B4` | `storw $0x0:s,0x0:s(r1,r0)` — `0` | 16-bit write |
| `0x00FF5406` | `0x2596` | `movd $0xff5406:l,(r4,r3)` | `ADDRESS_LOAD` |
| | `0x259C` | `loadw 0x0:s(r4,r3),r5` | 16-bit read |
| | `0x25A2` | `storw r5,0x0:s(r4,r3)` after `andw $0xF0FF` | read-modify-write |

`0x00FF5406` has two further read/modify/write sites, `0x1A14`–`0x1A22`
(normal) and `0x26040`–`0x26050`; in `p2test` the three sites are
`0x144A`–`0x1458`, `0x1E52`–`0x1E5E`, `0x267F6`–`0x26806`.

### The two address spaces are separate

`0x000F6006` and `0x00FF6006` are **different numbers**.  Nothing in the
decoded code establishes that the SC14448 maps them to the same hardware
register.  They are therefore reported, counted and reasoned about
separately everywhere in this repository.  Any future aliasing claim needs
independent evidence (a documented address map, or hardware observation) and
must be recorded on its own evidence level.

### Newly visible: `0x00FF4C00` and `0x00FF5000` (abs24)

The `data:l` form was invisible to the earlier scanner.  It resolves two
accesses into the `0x00FFxxxx` block **without** a register pair:

| Site | Instruction | Access |
|---|---|---|
| `0x15AE` (normal) / `0x1030` (p2test) | `storb r0,0xff4c00:l` | 8-bit write, `r0 = 0xFF` |
| `0x15B6` (normal) / `0x1038` (p2test) | `storb r0,0xff5000:l` | 8-bit write, `r0 = 0x08` |

Both sit in a block that is not reached in mode A (entry `0x1602`), so their
role is unknown.  They are the first **direct** (`abs24`) accesses to the
`0x00FFxxxx` block ever found in either image.

## 7. `0x01000000` — writers known, readers not found

| Site | Form |
|---|---|
| `0x25C4`, `0x2604`, `0x2E72`, `0x2F98`, `0x36BA`, `0x36EC` | `movd $0x01000000:l,(rp)` — `ADDRESS_LOAD` |
| `0x25D0` | `storw r2,0x0:s(r5,r4)` → **`SYMBOLIC` `0x01000000 + 2*r3`** |
| `0x2618` | the same pattern with `r4` |

No reader is found among the resolved forms.  That is **not** proof that no
reader exists: the base is always combined with an index
(`movzw`, `ashud $1`, `addd`) before use, so every access to this area is
`SYMBOLIC` or `UNKNOWN` by construction.

The proven index range in `0x25F90` is `1 … 511`: the counter at `0x937C` is
set to 1 (`0x25F98`) and the loop runs while it is `<= 0x200`, which is 511
iterations.  The stores therefore cover `0x01000002 … 0x010003FE`.  That span
is a consequence of the loop bound (see `fon-dialog-peripheral-init.md`), not
an address the code states.

## 8. Access widths

Every record carries the width of the *operation*:

* `0x000F6002`, `0x000F6400`, `0x000F6402`, `0x000F5402`, `0x000F6006` are
  accessed with `storw`/`loadw`, i.e. **16-bit**;
* `0xFF6006`, `0xFF5406`, `0xFF400A` are also `storw`/`loadw` (16-bit),
  reached through 32-bit addresses in a register pair (`movd …:l`);
* `0xFF4C00`, `0xFF5000` are `storb`, i.e. **8-bit**.

No 32-bit peripheral access to these registers exists in either image.

## 9. What the register state pass cannot do

* It does not propagate state across basic blocks, so a base loaded in one
  block and used in the next is `UNKNOWN`.  This loses links by design.
* It treats every call as clobbering all registers; no calling convention is
  verified.
* It cannot resolve indirect jumps, so blocks reachable only that way start
  from an unknown state.
* It never evaluates a `SYMBOLIC` expression into a number.

Consequence: the tables above list every access the code *states*, and a
subset of the accesses it *computes*.  Computed accesses remain open.
